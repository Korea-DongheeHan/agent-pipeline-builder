# {{pipeline_name}} — development orchestration

A **self-contained orchestration** generated by agent-pipeline-builder. It
runs from this directory plus `.claude/agents/{{prefix}}-*.md` alone (the
plugin is not required).

- Flow (SSOT): `pipeline.yml` — nodes, parallelism, branches, feedback loops
- Roles and expertise: `.claude/agents/{{prefix}}-*.md` (model, tools, system prompt)
- Task input and verdict criteria: `prompts/*.md`
- Execution engine: `scripts/run_graph.py` (state, branching, parallelism, resume)

## Execution modes

| Mode | How | Traits |
|---|---|---|
| **Runner** | `python3 scripts/run_graph.py pipeline.yml` | Deterministic, state-saving, resumable. Each node is an isolated claude session. Progress via console log. Zero orchestration cost |
| **Session** | Claude executes nodes with the Agent tool per `references/session-mode.md` | Live per-node subagent view and mid-run intervention. No resume; main-session overhead |

**The default mode is `settings.mode` in `pipeline.yml`.** Override only when
the user asks ("in session mode / let me watch", or "in runner mode").
Unattended, batch, and large runs suit the runner; observation, debugging,
and intervention suit the session.

## Procedure (when Claude executes this skill)

Call this skill directory **GRAPH_PIPELINE**
(`.claude/skills/{{pipeline_name}}`). Run from the project root (agent
definitions and build commands resolve from there).

0. **Determine the run context** — check the latest run in `.graph-runs/`
   (state.json):
   - no previous run / an unrelated new request → **new run** (start at 1)
   - the previous run is PAUSED/FAILED and this request continues it →
     **`--resume <RUN_ID>`**
   - a partial revision of the previous result → a **new run** whose
     requirement states "incremental revision based on the previous result",
     with the prior run's artifact paths attached
1. **Prepare the input** — condense the request into `--var requirement="..."`.
   If it is ambiguous, ask before running (headless nodes cannot ask).
2. **Disclose the cost** — one node execution = one claude session. State the
   expected session count from the node count and loop caps. For a thin
   single-file change, offer to do it directly instead.
3. **Run (runner mode — `settings.mode: runner` or user-selected):**
   ```bash
   python3 GRAPH_PIPELINE/scripts/run_graph.py GRAPH_PIPELINE/pipeline.yml --validate
   python3 GRAPH_PIPELINE/scripts/run_graph.py GRAPH_PIPELINE/pipeline.yml --var requirement="..."
   ```
   Run long executions in the background and watch the log. The run log is
   also written to `.graph-runs/<run-id>/run.log` automatically, so no
   redirection is needed. (Caution: redirecting into `.graph-runs/...` fails
   on a first run because the directory does not exist yet — if you must
   redirect, use a path that already exists.)
4. **SDD spec gate (on exit 3 / `⏸ PAUSED` — mandatory):**
   the pipeline pauses at `spec-gate` after the analyst finishes.
   1. Read `.graph-runs/<run-id>/outputs/analyst.iter1.md` — it contains the
      spec draft and a "questions to confirm" section.
   2. Put those questions to the user in **one AskUserQuestion round
      (max 4 questions)**, with the analyst's recommendation as the first
      option marked "(recommended)". If the section says "none", show the
      spec summary and get consent to proceed.
   3. Condense the decisions into one paragraph and resume:
      ```bash
      python3 GRAPH_PIPELINE/scripts/run_graph.py GRAPH_PIPELINE/pipeline.yml \
        --resume <RUN_ID> --var requirement="..." \
        --var decisions="① scope: ... ② architecture: ... ③ done criteria: ..."
      ```
      (The succeeded analyst is served from cache, and the confirmed spec is
      injected into the implement, test, QA, and review prompts. **Never
      start implementation without a confirmed spec.**)
5. **On success** — summarize the `.graph-runs/<run-id>/` artifacts (per-node
   outputs, acceptance verdicts). **On failure** — report the failed node and
   reason from state.json, and offer `--resume <RUN_ID>` after the cause is
   fixed.
6. **Session mode (`settings.mode: session` or requested)** — instead of 3–5,
   orchestrate the graph directly with the Agent tool (subagent_type = the
   node's agent) following `references/session-mode.md`. Handle gate nodes
   with AskUserQuestion on the spot.
7. **Wrap-up** — commits and merges are human gates; proceed only after the
   user reviews the result and confirms. At the end of the completion report,
   **optionally ask for improvement feedback** (never insist): "anything
   disappointing about the result or the pipeline behavior?" — map any
   feedback to a fix target using the evolution table below.

## Evolution (feedback → fix target)

This pipeline is an operated system, not a static artifact. When the same
feedback repeats twice, proactively propose the fix.

| Feedback type | Fix target |
|---|---|
| Output quality (omissions, below criteria) | `prompts/*.md` verdict criteria and acceptance contract |
| Role behavior (wrong approach, convention violations) | `.claude/agents/{{prefix}}-*.md` |
| Awkward order, branching, or loops | `pipeline.yml` workflow |
| Too slow or too expensive | merge nodes, lighten agent `model:`, reduce loop `max` |
| Too many / too few questions (spec gate) | the questions-to-confirm contract in `prompts/analyst.md` |

Apply changes with the **`agent-pipeline-builder:edit` skill** when the
plugin is installed; even for manual changes, add one row to `CHANGELOG.md`
(date, request, files changed).

## Configuration changes

- Flow changes: `pipeline.yml` (syntax: the header comments and the
  agent-pipeline-builder spec)
- Verdict criteria and task input: `prompts/*.md` / roles and models:
  `.claude/agents/{{prefix}}-*.md`
- After any change, always run `--validate` then `--mock`
- With the plugin installed, **`agent-pipeline-builder:edit`** performs node
  additions, loop tuning, and agent changes safely ("add X to the pipeline")
